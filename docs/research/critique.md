1. **blocker — cloudpickle will pickle `predict` by reference, not by value.** The plan builds the closure in `stealth/bundle.py` inside an installed package. cloudpickle serialises functions that live in an importable module as `(module, qualname)` references; the lane sandbox has no `stealth` package, so the upload fails at smoke (`ModuleNotFoundError`), and any helper (`gaussianise`, member loaders, the numpy MLP forward) referenced from `stealth.*` fails the same way. Fix: `cloudpickle.register_pickle_by_value(stealth)` (and every submodule the closure touches) before dumping, or build the closure in a standalone script with only stdlib/numpy/pandas/scipy/lightgbm/xgboost/catboost imports *inside* the function body. Make `pkl_check` prove it: run the subprocess with `cwd=/tmp`, `python -I`, in a venv where `stealth` is NOT installed, and assert `stealth` is absent from `sys.modules` after `predict()`. Also scan the pickle bytes for `b"stealth"` alongside `b"torch"` (torch 2.15 is installed on the sandbox, so a stray import passes locally and dies in the lane).

2. **blocker — the pre-commit secret scanner, as specified, blocks every results commit.** "40+-char hex/base64 key-shaped strings" matches every git sha (40 hex) in `NN-metrics.json`/`NN-results.md` and every `.sha256` file (64 hex). Fix: scan only for `EIQ_API_KEY\s*=\s*\S{8,}`, `X-API-Key`, `ghp_`, `github_pat_`, `gho_`, `AKIA`, and `-----BEGIN`; allowlist `^[0-9a-f]{40}$|^[0-9a-f]{64}$`. Hooks are not versioned: handoff 00 must run `git config core.hooksPath scripts/hooks`, or the hook never executes on the laptop.

3. **major — public repo + committed `.pkl` + committed OOF/search results = free model for every competitor.** Anyone can clone `models/stealth_v1.pkl`, run it on the live parquet and submit identical predictions (and the user plans to stake later). Handoff results also publish the config that won. Fix: ask the user to flip the repo to private (GPT works identically after `gh auth login`); never commit `.pkl` (ship it laptop→platform directly via `predict --upload`, keep sha256+manifest only); keep metrics but strip winning hyper-parameters from results files, or accept the leak knowingly.

4. **major — the scenario score `S = 3·FIT − ρ_b·B − ρ_c·C` ignores the zero rule and the benchmark's per-round distribution; it is computed with an average B that never occurs.** Live benchmark FIT is 0.009 mean with per-round std ≈0.03–0.04 (round 30's daily walk swings −0.052…+0.074), so B<0 in ~40% of rounds → UNQ = 0 there, and in the B>0 rounds the conditional B ≈ 0.03 (comparable to our FIT). Working the algebra per regime (ρ=0.6, O=0.027, p_b=0.5): benchmark-positive rounds lose ~0.001, benchmark-negative rounds gain ~0.010 *in FIT*, net ≈ +0.004. The gain exists but comes from down-weighting a low-Sharpe benchmark direction, not from "UNQ credit", and its sign flips if live B is actually ≥0.02. Fix: evaluate neutralisation per era with the gating (`everestapi.scoring.unq20` already implements the zero rule; note the sandbox SDK is 0.4.1 and `unq20` has NO `zero_rule` kwarg — the plan's call signature is wrong), against a synthetic benchmark = surrogate direction + noise calibrated to live FIT ~N(0.009, 0.035²), and report the three regimes separately. Also: I verified `download_dataset(split='minera_model')` for exped_8055 is Spearman 1.000 with the live `v1_sherpa` file (`/home/climber/.claude/jobs/8bc89d82/tmp/futures_minera_model.parquet`) — the reference ambiguity in risk #4 is smaller than stated; keep p_b ≤ 0.75 for the FIT-cost reason, not the reference reason.

5. **major — the admission gates are statistically infeasible as written.** Per-config FIT SE ≈ 0.0033 (186 effective eras), yet M2/M4/M11 demand "+0.001 FIT with non-overlapping 1-SE". Unpaired, +0.001 can never clear. Fix: paired 20-era block bootstrap of the *difference* in per-era FIT between two configs (SE_diff ≈ SE·√(2(1−r)) ≈ 0.0015 for r≈0.9) and gate on `P(diff>0) ≥ 0.8`. Relatedly, `mean FIT − 0.5·SE` as the search objective is cosmetic: SE is ~constant across configs, so it never changes the argmax.

6. **major — 100–150 Optuna trials will select noise (winner's curse).** Expected tuning gain ≤0.002 FIT vs selection noise 0.0033; the best of 150 noisy trials is biased upward by ~2.5 SE (≈ +0.008), which is exactly what "OOF FIT ≥ 0.030" at M7 would show while being fake. Fix: ≤20–30 trials over a coarse grid, average the top-k configs instead of picking one, confirm the pick on the forward block only once, and spend the multi-hour budget on members (targets, feature bags, families) rather than trial count. Treat any OOF > M1 + 0.004 as suspect, not success.

7. **major — feature-selection leakage inside CV.** The 53-feature `|sharpe|>0.1` arm, the top-10 "core proxy", and the benchmark surrogate are all selected/fitted on the full train span, including every test fold. Fix: select features and fit the surrogate inside each fold on its training eras only (nested), or on eras < 2800 which are excluded from scoring anyway. Better still, compute ρ_b exactly on the validation split (v1_sherpa validation file exists, no targets needed) instead of a surrogate.

8. **major — early stopping on the test fold inflates OOF.** "Early stopping per fold for tree count only" still uses the scored fold to pick its own tree count. Fix: inner purged split inside each training fold for ES, or a fixed tree-count grid; only predictions made with the frozen median count are reported as OOF.

9. **major — `p_b` tuned on the diag lane is biased too.** Validation-board unq/fit ≈ 0.2–0.3 vs live 0.5–0.6 implies v1_sherpa is much stronger on validation (6566–7957) than live, i.e. likely still in-sample there. A sweep on the diag lane will pick a p_b that is too high for live. Fix: use diag results only for direction (does neutralisation cost FIT?), choose p_b from the live-calibrated simulation in item 4, and read the canary's live UNQ/FIT ratio after ~10 rounds before raising p_b.
